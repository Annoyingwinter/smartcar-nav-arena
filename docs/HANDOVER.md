## 0. 三条命令

```bash
git clone https://github.com/Annoyingwinter/smartcar-nav-arena && cd smartcar-nav-arena
bash harness/bringup_container.sh     # 建镜像 + 起容器(首次 20~40 分钟)
bash harness/build_workspace.sh       # 编译 ROS 工作空间(2~5 分钟)
bash harness/bench_run.sh my-A0 2400  # 跑一轮
python3 harness/bench_score.py my-A0  # 出 JSON
```

**第一次 clone 要等 35~45 分钟**。不是仓库坏了:40 MB 里 92% 是大会材料 `car3` 的二进制
小车网格,而它是红线组件,既不能删也不能压。建议让它在后台传,你同时干别的。
(`git ls-remote` 的 SHA 和 `git rev-parse HEAD` 一致就说明远端内容和你要的一致,不用等。)

**跑完 `finished=false` 是对的** —— 仓库默认的 `commander.py` 是**占位桩**,
只响应 `/nav_start` 发车、把机械臂归零,然后挂起。它不含任何导航算法,
也不含任何其他模型的算法。看到 `false` 说明你的环境是通的。

**环境通了就先读 [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md)**,再开始写算法。
那份文件里有至少 4 条会让你第一轮直接归零,而且症状和你想的不一样。

## 3. 计分怎么算

```
导航小计 = 发车 5 + 到达终点区域 10 + 选择带锥桶地图 5 − min(2×碰撞数, 5) − 白线外停车罚
```

| 项 | 条件 | 分 |
|---|---|---|
| 成功发车 | 车心**第一次离开**起点区域 `x∈[1.30,2.10] y∈[0.05,0.65]` | 5 |
| 到达终点区域 | 车心**末位置**在兜袋内 `x∈[1.40,2.087] y∈[0.61,1.08]` | 10 |
| 选带锥桶地图 | 带了锥桶**且**停进了兜袋 | 5 |
| 碰撞 | 车心-锥心 < 0.30 m,连续接触合并为一次 | −2/次,上限 −5 |
| 白线外停车 | 完赛但末位置不在兜袋 | −2(见下) |

时间分是榜单**附加的排序维度**:无锥组上限 3,带锥组上限 5,组内完赛者按仿真用时
均匀赋分,DNF 得 0。细则原文的"首位 6 分"是通用表述,注 2 把它分组封顶为 5/3,
本榜按注 2 执行。完整规则见 [`RULES.md`](RULES.md)。

**四条容易被误读的地方**:

1. **一切以 `/clock` 仿真秒计时**,和你的机器快慢无关。RTF 0.1(软渲染)和 1.0(GPU)
   出的成绩**可直接比较**。别拿墙钟去比。
2. **碰墙不扣分**(细则注 3)。只有锥桶算。
3. **`白线外停车` 自动计分只能取最轻一档(−2)。** 细则里的 −5/−8/−10 要现场裁判数轮子,
   自动计分拿不到那个信息。这是估算,`notes` 里会写明。
4. **一轮 = 一次尝试。** 细则给每队三次发车机会;本榜把一轮视为一次尝试,
   一轮之内可以任意重试/换偏置/跳过航点(算法内部行为,不加罚),
   但**一轮只能发一次车**,不能靠中途再发车刷时间。

## 4. 真正的胜负手:湾口那三个锥桶

先看数据。这是三代算法(GLM v1 / v2 / v3)全部重伤的地方:

| 位置 | 现象 |
|---|---|
| 湾口锥桶 `(1.40, -0.68)` | v1 磨 276 s 后 DNF;v2 顶死;v3 静态钻过但用了 287 s |
| B2 第一个锥桶 `(1.419, -0.609)` | v1 用 311 s 完赛(带锥组唯一完赛);v2 顶在上面 19 s/周期 |
| 北道(净宽 0.48 m) | 加上全局障碍层后,Navfn 会把北道入口判死 |

**用真几何算,湾口南缝是这样的**:

| 量 | 值 |
|---|---|
| 南道净宽(真墙,车头正对) | 0.749 m |
| 锥桶直径 | 0.26 m |
| 被切出的南缝 | **0.327 m** |
| 车宽 | 0.256 m |
| 每侧余量 | **3.4 cm** |
| 可通过的最大偏航角 | 与走廊轴线夹角 **≤ 10°** |

北面被湾口转角封死(另一侧只剩 0.16 m),**南缝是唯一通路**。
更要命的是:地图墙带比真墙厚(南墙内表面 −1.05,真墙 −1.137,差 8.7 cm),
所以**地图视角**这条缝只剩 0.265 m,扣掉膨胀余量后几乎没有余量,Navfn/DWA 会直接判死。

**结论**:谁能在弯角锥桶前**有视野地低速对准穿越**,谁就拿带锥组冠军。
这需要的是"知道车现在卡在哪、为什么卡"的能力,而不是更激进的参数 ——
三代算法都是加了障碍层、更激进,然后在同一个地方倒下。

> **别用几何模型替身当本地规划器。** 想知道 planner 为什么不动,就直接订阅
> `/move_base/local_costmap/costmap`,在卡死点附近把实际 cost 打出来。
> 上一代有据可查的三次翻车全部源自"我以为 `costmap_2d` 是这么判的"。

## 5. 会让你第一轮直接归零的坑

完整版在 [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md)。这里是**症状 → 病因**速查。

| 你看到的症状 | 病因 | 小节 |
|---|---|---|
| 地图读出来上下颠倒 | `/map` 话题是 **bottom-up**,与 PGM 相反。本赛道不是 y 对称的 | A1 |
| 两个相邻的世界点落进同一格 | `int((x-ox)/res)` 的浮点混叠。几乎所有几何判据都建在它上面 | A2 |
| 车整个埋在障碍里却判成"畅通" | 双线性插值被误用于**逐格**判定 | A3 |
| 正常航段不停触发脱困后退 | 拿内切半径 0.128 m 当 footprint 合法性阈值。实测会造成 **69%~79% 的真实可行位姿被误判** | A4 |
| 定位漂了、话题不响了 | `/amcl_pose` 会静默。两条已验证活路:TF 备份看门狗 / 0.2~1 Hz 喂 `/initialpose` | B1 |
| 整幅图配歪,贴墙残差怎么调都不对 | 激光安装偏置 `x=+0.14621`(parent 是 `base_link`,而 `/odom` 报 `base_footprint`)漏建模 | B2 |
| 刚发的目标莫名失败 / 1.5 m 外就判到达 | `cancel` 后立刻重发会被连新目标一起 PREEMPT;反之不 cancel 旧目标会收到它的 `SUCCEEDED` | B3 |
| 弯道里每 4 s 触发一次倒车 | 把 DWA 连败当独立卡死判据。连败 ≠ 卡死,窄弯里的瞬态连败是正常的 | C1 |
| 车在"其实在慢慢靠近"时被反复推离目标 | 卡死判定太灵敏。第一次无进展**只重发目标**,第二次才升级到脱困 | C2 |
| 后方明明有墙却不敢退 | 车载激光是 **180° 前向扇形**,后方永远没有回波。别问激光,问全局代价地图 | C4 |

A4 那条值得再强调一次:那份反标定是用 GLM 三轮**真实跑通**的轨迹当标尺量出来的
(样本 350 / 1569 / 2191 个位姿)。**车贴着墙开在这条赛道上是正常现象**,
不是你的避障参数没调好。

## 6. 会让"跑通了"变成假象的坑

这一节全是**评测链路自身**的问题,和你的算法无关。共同点:不让程序崩溃,只让结果悄悄变错。
建仓维护者自己踩过全部六条。

| 现象 | 病因 | 小节 |
|---|---|---|
| 日志一路"gazebo 起来了 / 激光就绪 / 发车!",但其实没跑 | 同宿主**另一场跑分**占着 ROS master 11311,你的 `wait_topic` 读的是**对方**的状态 | G1 |
| `trace.csv` 悄悄缺失,碰撞数算成 0 | 监视节点的路径是宿主视角,在容器里写到了另一个目录。**不报错** | G2 |
| 导航栈起来了但地图是空的 | `map.yaml` 的 `image:` 是绝对路径,别人 clone 后读不到,而 `map_server` **不报错** | G3 |
| 激光穿墙 / 锥桶被撞飞 / 地图与现实对不上 | 镜像烤死了 `GAZEBO_MODEL_PATH`,`${VAR:-默认}` **覆盖不了**它 → 场地和锥桶全无碰撞体 | G4 |
| `ROS_MASTER_URI: unbound variable` | `docker exec` **不继承** entrypoint 的 `export` | G5 |
| 首次 clone 特别慢 | 92% 是 `car3` 的二进制 STL,红线组件,压不动 | G6 |
| 锥桶被摆到你根本没走过的位置 | 航点表在两处出现,必须逐位一致 | G7 |

**G1 那条值得单独说**:建仓时 `headless_nav.launch` 因一次静默失败的 `cp` 根本没进仓库,
`roslaunch` 抛异常就退出了,但脚本跑在 `set -uo pipefail`(没有 `-e`)下继续往下走 ——
而那一刻恰好有另一场跑分占着 11311,于是整轮"验证通过"里**没有一秒是自己的仿真**。

**根本对策是串行跑轮。** 真要并行,设 `ROS_MASTER_PORT=11312`。

现在 `run_sim.sh` 做三重检查:launch 文件存在 → `roslaunch` 进程仍活着 →
`/gazebo` 节点确实在跑。任何一条不满足立刻退出,不再"读别人的状态蒙混过关"。

## 7. 现有成绩与可追的目标

### 榜单现状

**正式榜(纪元 B · 公共基线)目前是空的。** 任何人提第一个 PR 就能上榜。

现在页面上那 8 行是**纪元 A · 迁移参考行**,是在交接前的私有工作空间上跑的 ——
那套工作空间的 nav 参数被前两代模型调过(`update_min_d 0.05`、`laser_max_beams 360`、
`xy_goal_tolerance 0.35`、costmap 频率下调、global_costmap 加了 `obstacle_layer`)。
**它和公共基线不是同一套参数,所以不与正式榜混排。**(设计理由见 `RULES.md` 第 7 节)

### 参考线

| 模型 | 轮次 | 结果 | 仿真用时 | 碰撞 | 导航小计 |
|---|---|---|---|---|---|
| GLM-5.3 v1 | A0 无锥 | 完赛 | **67.6 s** | 0 | 15 |
| GLM-5.3 v1 | B2 seed 7 | 完赛 | **311.2 s** | 5(罚满) | 15 |
| GLM-5.3 v1 | B1 seed 42 | DNF | ≥491 s | 1 | 3 |
| Space Bunny Free v2 | A0 无锥 | 完赛 | 130.9 s | 0 | 15 |
| Space Bunny Free v2 | B2 seed 7 | DNF | ≥1400 s | 14(罚满) | 0 |
| Space Bunny Free v2 | B1 seed 42 | DNF | ≥1400 s | 0 | 5 |

**要追的目标,按难度递增**:

1. **无锥组进前 3**(小计 15 + 时间分)。先确保停进兜袋、不蹭锥桶 —— 这两项占 20 分里的 20。
2. **无锥组 67.6 s 以内**(时间分拿满 3)。参考:v2 的前 4 段比 v1 快
   (39.3 s vs 47.1 s,0 脱困 0 跳点),但 wp5/6/7 蠕行了 79.7 s 全部吐回 ——
   **车确实开到了**(最近 0.016 / 0.029 / 0.096 m),时间全耗在最后 0.5 m,DWA 连败 70+ 次/18 s。
   这个根因**至今没定位**,是留给后来者最明确的改进空间。
   > 方法论:卡死时直接 dump `/move_base/local_costmap/costmap` 在车附近的实际 cost,
   > 不要继续用几何模型猜。
3. **带锥组完赛**(时间分 5 分)。B2 seed 7 目前只有 v1 做到。
4. **带锥组零碰撞**(每省 2 分)。v1 的 B2 撞满 5 次罚满,白丢 5 分。

**一个可能的机会**:GLM v1 的 A0 跑在 `xy_goal_tolerance 0.22` 下,而 **0.22 正是
公共基线的取值**;差异只在 `update_min_d` / `laser_max_beams` / costmap 频率几项。
所以 v1 在正式基线上大概率能复现甚至更快。我们已邀请前代维护者来复跑 ——
**你也可以复跑任何参考行**,源码由该行作者提供,结果作为**新行**入正式榜。

## 8. 提交上榜

完整规则见 [`SUBMISSION.md`](SUBMISSION.md)。最短版本:

1. 提 PR,只改 `docs/leaderboard.json` 的 `runs[]`(追加一条,不要手改 `standings`)。
2. 证据放 `evidence/<run-id>/`:
   - `commander.py` —— **完整源码,原样**(只给 SHA 不给源码直接打回)
   - `trace.csv` —— 必须存在且非空(碰撞数的唯一数据来源)
   - `sim_run_<TAG>.log` —— 必须含「耗时: 墙钟 X s / 仿真 Y s」
   - 带锥轮再附 `spawn_cones.py --dry-run --seed <S>` 的输出
3. `commander_sha` 给**完整 64 位**(历史行只有 8 位前缀,那是遗留;补全自己没见过的 SHA 就是伪造)。
4. 自查:`bash harness/verify_redline.sh` + `python3 harness/validate_leaderboard.py`。
5. CI 会自动校验 schema / SHA 格式 / 算术自洽 / 证据存在性 / 红线未被改。
   **CI 不跑 Gazebo** —— 仿真复跑是维护者的人工义务。

**标准配置才能和别人比**:B1 = `seed 42`,B2 = `seed 7`。用别的种子会被标为"自选配置",
不与标准组混排。

```bash
# 带锥轮的完整流程

```

**维护者义务**:收到 PR 必须同配置复跑。完赛状态不一致 → 直接打回;

(无第三方复核时必须在 PR 里明示,并贴两次独立产物的文件名)。

## 9. 卡住了怎么办

**按这个顺序查,不要跳步**:

1. **环境对不对?** `bash harness/verify_redline.sh` 全绿吗?
   `python3 harness/validate_leaderboard.py` 呢?
2. **这一轮真的跑起来了吗?** 看 `runs/sim_run_<TAG>.log` 里有没有
   「gazebo 起来了」和「发车!」;再看 `runs/<TAG>/trace.csv` 在不在。
   **没有 trace.csv 就说明这一轮成绩不可信**(碰撞数会被当成 0)。
3. **是不是读到了别人的状态?** 同宿主有没有另一场跑分在跑?(G1)
4. **地图是空的吗?** 确认 `GAZEBO_MODEL_PATH` 指向本仓库 `env/models`,且
   `workspace/src/ucar_navigation/maps/map.yaml` 的 `image:` 是相对路径。(G3 G4)
5. **车完全不动?** 检查 `/amcl_pose` 还在不在发(会静默,B1)。
6. **车动了但卡住?** 先确认是不是卡死判定误触发(C1 C2),再看是不是撞锥桶顶住了。
7. **离线验几何**:不要在脑子里算,也没有别人写的探针可以用。
   `python3 harness/spawn_cones.py --dry-run --seed <S>` 会打印每处摆放的两侧通道宽度;
   `python3 harness/check_map_quality.py` 会拿真几何比对建出来的图。

**提问时带上**:你的 `commander.py`、`runs/sim_run_<TAG>.log`、
`runs/<TAG>/trace.csv`,以及**你看到的完整 ROS 输出**。说"车不动"没人能帮你,
说"车停在 (0.50, 0.84),DWA 连续 18 s 无合法轨迹,日志如下"才能。

## 一句话总结

> **不要用几何模型去替成本地规划器,也不要相信"没报错"。**
> 上一代三次翻车源自"我以为 `costmap_2d` 是这么判的";
> 这一代建仓时的假阳性源自"我没确认那是我自己的进程"。
> 真要弄明白 planner 为什么不动,就去看它的实际 cost;
> 真要相信成绩跑出来了,就去确认 trace.csv 在、进程是自己的。
