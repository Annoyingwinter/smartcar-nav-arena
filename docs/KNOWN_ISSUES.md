## A. 会让整场比赛读错数据的坑(最优先)

### A1. `/map` 话题的行序是 bottom-up,与 PGM 相反

**现象**:从 `/map` 拿栅格自己解析时,若按 PGM 的"首行 = 顶行"去解释,整张图会**沿 y 轴镜像**。
本赛道**不是 y 对称的**(南墙 y=-1.15 / 内墙 y=-0.37 / 北墙 y=+1.10),镜像后代价地图完全错位。

**v2 实测后果**:车在 `(-0.30, 0.56)` 处明明姿态合法(真实角点净空 0.247 m),
镜像图里算出来是 **0.000 m** → 判成"楔住" → 触发无谓的后退 → 单个航点从 3.4 s 烧到 57.7 s。

**规范依据**:`nav_msgs/MapMetaData.msg` 写的是「cell (0,0) … origin」,
`costmap_2d::Costmap2D::getIndex() = y*width + x`,即 y=0 在 `origin.y`,即**左下角**。
而 PGM 格式第 0 行是**图像顶行**(= 最大 y)。两者相反。

**怎么做**:解析时显式声明行序,不要靠默认。

```python
# 反例
rows = [msg.data[r*w:(r+1)*w] for r in range(h)]   # 把它当顶行 -> 镜像
# 正例:自己写栅格解析器时加一个显式参数
MapGrid(w, h, res, ox, oy, data, row_order='bottom')   # /map 话题
MapGrid(w, h, res, ox, oy, data, row_order='top')      # PGM 文件
```

**复核**:拿一张左右/上下明显不对称的图走一遍你的解析,看 `origin.y` 那一行的墙位对不对。

### A2. `int((x - ox) / res)` 会因浮点误差发生混叠

**现象**:`res = 0.025` 在二进制里不精确。`(0.05 + 5.0) / 0.025` 算出
`201.99999999999997` → `floor` 得 `201`;而 `(0.025 + 5.0) / 0.025` 正好是 `201.0` → 也是 `201`。
**两个相距一格的世界点落进同一个格。**

**v2 实测后果**:半径 1.6 m 的实心圆只点亮 **4793** 格(应为 12853),
圆心附近漏出一整条缝。于是"被实心障碍完全埋住"的车,被判定成"周围还有合法姿态"。

**为什么致命**:几乎所有几何判据(姿态合法性、是否卡死、偏置点是否在空地、
锥桶是否挡路)都建在这个索引函数上。索引一混叠,这些判据全部失真,而且**不报错**。

**怎么做**:先四舍五入到 1e-9 再 `floor`,或者干脆用 `round()`。

```python
c = int(math.floor(round((x - ox) / res, 9)))
```

**复核**:对半径 R 的圆统计点亮格数,与 `πR²/res²` 比。差得多就是混叠了。

### A3. 双线性插值只能用于求连续最优,**不能用于逐格判定**

**现象**:`dist_float()` 对平方距离场做双线性插值。求平移量时这是对的
(目标函数在平移量上连续,最优点唯一)。但用它做"某格是不是 lethal"会出错:
顶点所在格 `dist2 = 0`,相邻自由格 `dist2 = 1`,插值后得到 ~0.5 → 开方 ~0.7 格 ≈ **1.75 cm > 0**。

**v2 实测后果**:车整个埋在实心障碍里,四角"净空"算成 0.021 m,于是
`pose_is_legal` 判**合法**、`stuck_hard` 判**不死** —— 一个彻底被埋住的车被当成了畅通。

**怎么做**:合法性判定逐格查表(footprint 顶点落在哪一格就查那一格),
插值只留给配准/优化类用途。

```python
c, r = grid.cell_of(px, py)
if grid.dist2[r * grid.w + c] <= 0.0:   # 这一格本身是 lethal
    return False
```

**复核**:造一张全实心的小栅格,查内部点的净空 —— 必须是 0。

### A4. `footprint` 合法性阈值**不是内切半径 0.128 m**

**现象**:`costmap_2d` 里 `INSCRIBED_INFLATED_OBSTACLE = 253` 这个常数很容易被误读成
"footprint 落进 253 带就非法",于是拿 `inscribed_radius`(本车 0.128 m)当阈值。

**v2 实测反标定**(用 GLM 三轮**真实跑通**的轨迹当标尺,量角点净空):

| 轮次 | 样本 | 角点净空中位数 | 最紧 |
|---|---|---|---|
| GLM A0 | 350 | 0.087 m | 0.000 m |
| GLM B2 | 1569 | 0.022 m | 0.000 m |
| GLM B1 | 2191 | 0.023 m | 0.000 m |

按 0.128 m 判,会把 **A0 69% / B2 76% / B1 79%** 的真实可行位姿误判成非法,
于是正常航段上不停触发脱困后退。**车贴着墙开在这条赛道上是正常现象。**

**怎么做**:用能标定门槛的那个值。v2 取 `0.005 m`(给 5 cm 格量化留余量,
实测对 A0 只误判 1.4%)。**更好的做法是自己跑一遍反标定**。

**复核**:拿 GLM 的 `runs/*/trace.csv`(如果你的仓库里有)或任何"车确实开过去了"的
轨迹,量角点净空分布,门槛必须 ≤ 最紧值。

## B. 定位与话题

### B1. `/amcl_pose` 会静默

**现象**:AMCL 发几十条 `amcl_pose` 之后就停发。GLM v1 的 B1 轮里,
定位看门狗因此在长局中完全失效 —— 磨得越久越瞎。

**已验证活着的两条路**:

1. **TF 备份看门狗**:不依赖 `/amcl_pose`,直接 `lookup_transform('map','odom')`;
   TF 由谁发都行,并且可以自己发。
2. **低频喂 `/initialpose`**:把 `/odom` 真值(在 map 帧下)当 `/initialpose` 喂回去,
   频率 **0.2~1 Hz** 就够。

**注意纠偏是滞后一拍的**:`/initialpose` 生效后 AMCL 还要重新收敛,收敛期间
代价地图已经按旧位姿摆好了。v2A0h 实测:1 Hz 纠偏把偏差压到 4.7 cm,卡死照旧 —— 
自锁链不是靠定位精度打破的。

**v2 的最终做法**:`/odom` 与世界系重合(发车位姿与 launch 初始位姿逐位相同,
用 odom 位姿打真墙中位误差 4 mm),而基准图与世界系零偏移,所以 `map->odom` 应当是
**单位变换**。于是直接自己发 `map->odom`(identity),AMCL 留作诊断。

### B2. 激光有安装偏置,不建模就会把整幅图配歪

**现象**:`car3.urdf` 里 `laser_joint` 的 origin 是 `x = +0.14621`,**parent 是 `base_link`**;
而 `/odom` 报的是 `base_footprint`(车中心)的位姿。两者差这一个 x 偏置。

**v2 实测后果**:漏算它,发车时车头朝南(yaw = -π/2),这个偏置整个落到世界系 -y 上,
`register` 于是每轮稳定解出 `s = (0.000, -0.135)` —— 与 0.146 m 吻合(差的 1.1 cm 正好是半墙厚)。
表面上"贴墙残差只有 0.3 mm、图没问题",但偏置门限判定失败 → `run_calibration` 返回 False
→ **连锁把本该由里程计接管的 `map->odom` 让回了 AMCL**。

**怎么做**:把激光偏置显式建进投影。

```python
lx, ly = 0.14621, 0.0      # 来自 urdf 的 laser_joint, 配 base_link -> base_footprint
tx = ox + lx*ca - ly*sa
ty = oy + lx*sa + ly*ca
px, py = tx + r*math.cos(a)*ca - r*math.sin(a)*sa, ...
```

**复核**:车朝南时端点集合应整体沿 -y 平移 0.146 m;车朝东时沿 +x。

### B3. `cancel` 之后立刻重发,会把**连新目标一起** PREEMPT

**现象**:`SimpleActionClient.cancel_all_goals()` 之后紧接着 `send_goal()`,
新目标经常被上一个 goal 的取消动作连带作废,状态停在 PREEMPT/ABORTED,
你会看到"刚发的目标莫名失败"。

**v2 实测**:另一面 —— `close_enough` 判到达时**没有** cancel 旧目标,
客户端 0.4 s 后把旧目标的 `SUCCEEDED` 报给新目标,于是车还在 **1.5 m** 外就被判"到达"了航点 2
(该轮用时 0.4 s)。

**怎么做**:到达时**先 cancel 旧目标再发新目标**,并且对收到的成功做距离复核 ——
离目标太远的一律不认。

```python
if state == GS.SUCCEEDED:
    d = goal_dist()
    if d > CLOSE_ENOUGH + 0.20:      # 上一目标的终态报错了对象
        return                        # 不认, 继续跑
```

## C. 决策层

### C1. DWA 连败 **不等于** 卡死

**现象**:窄弯里 DWA 在控制频率(10 Hz)上短暂连败是**正常现象**。
把它当独立卡死判据,会得到"发目标 → 4.1 s → 脱困 → 倒车 0.30 m → 目标更远"的循环,
比不脱困还糟。

**v2 实测**:每个航点都准时 +4.1 s 触发一次倒退。

**怎么做**:DWA 连败只作为**佐证**附在"距离没在缩短"这个理由里,不独立触发。

---

### C2. 卡死判定宁迟勿早,第一次无进展只重发目标

**现象**:10 s 一判卡死就后退,会让车在"其实在慢慢靠近"时被反复推离目标。

**v2 实测(同一赛道,只改这一条)**:

| 配置 | 总用时 | 脱困次数 | 跳过航点 |
|---|---|---|---|
| `STUCK_TIME=10` + 一判就退+偏置 | 219.1 s | 3 | 2 |
| `STUCK_TIME=18` + 第一次只重发 | **130.9 s** | **0** | **0** |

GLM v1 在西走廊上段单段用了 26.6 s 也没判过死 —— 它快的真正原因就在这里。

**怎么做**:阈值 18 s;第一次无进展只做 `clear_costs + 重发同一个目标`(约 0.5 s),
第二次才升级到脱困(取消 + 清图 + 后退/原地转)。

---

### C3. 全局代价地图的障碍层是绕锥的关键,但会判死北道入口

**现象**:不加 `obstacle_layer`,Navfn 看不见锥桶,会规划直线穿锥桶。
加上之后 Navfn 会绕,但**北道入口(那个 60° 拐弯)会被判死** —— 因为地图墙带比真墙厚,
膨胀带在拐角处闭合。

**怎么做**:两者要配套 —— 加障碍层的同时给一个"拐角允许通行"的机制
(v2 试过 `cone_mode`,需要自己实现);或者在拐角航点上加横向偏置重试。

---

### C4. 局部代价地图里看不到车后方

**现象**:车载激光是 **180° 前向扇形**(`min_angle=-1.57`, `max_angle=+1.57`, 720 样本),
**不存在 360° 假障碍环**,但**后方永远没有回波**。

所以任何"拿激光判断后方是否安全"的写法都是自欺欺人 —— `rear_clearance` 对本车恒返回 `max_range`。
后方安全只能问**全局代价地图**(它有 static 层,墙的位置是已知的)。

**怎么做**:倒车前查全局代价地图;若地图也判不了,改成**原地转一小段**把侧向/后方扫进视场。

**复核**:发车点静止时看 `/scan` 的最小/最大值 —— 应分别是 ~0.33 m 和 ~3.6 m,
说明激光忠实打在真墙上,而不是有一个假的近距离环。

## D. 几何:弯角锥桶(三代算法全部在此重伤)

### D1. 湾口锥桶(1.40, -0.68)的真实尺寸

**这是本赛道最难的点,三代算法(GLM v1 / v2 / 更早的迭代)全部在这里重伤。**

用**真几何**(`env/round1.world`)而不是地图来算:

| 量 | 值 |
|---|---|
| 南道净宽(真墙,车头正对处) | 0.749 m |
| 锥桶直径 | 0.26 m(半径 0.13) |
| 被切出的**南缝** | **0.327 m** |
| 车宽 | 0.256 m |
| 每侧余量 | **3.4 cm** |
| 可通过的最大偏航角 | 与走廊轴线夹角 **≤10°** |

北面被湾口转角封死(另一侧只剩 0.16 m),所以南缝是唯一通路。

**更糟的是**:地图的墙带比真墙厚(南墙内表面在 -1.05,真墙在 -1.137,差 8.7 cm),
于是**地图视角**这条缝只剩 **0.265 m**,扣掉膨胀余量后几乎没有余量,
Navfn / DWA 会直接判死。

**结论**:
- 按地图算出来的走廊宽度,必须回真几何复核一遍 —— 几厘米在北道(净宽 0.48 m)就是生死之差。
- 想拿下这一轮,只能减 `footprint_padding`(代价:到处都敢贴墙 5 cm)或接受碰。

**2026-10-04 更新:已经有人走通了。** `glm-v49-b1` 那一轮实测穿过湾口,维护者从 `trace.csv`
独立复核(锥心 (1.399,-0.680) 半径 0.13,南墙真值 -1.137,车半宽 0.128):

- 车心可行带 y ∈ [-1.009, -0.938] —— **只有 71 mm 宽**;
- t=187.3 s 进入带内,192.5 s 车心到 x=1.286,继续西行至 x=0.351 穿出;
- 锥桶正前方车-锥漆面净空 **20 mm**(同点车-墙 52 mm,合计≈整条缝)。

所以真实难点**不是缝太窄**,而是**能不能在随机停姿下把车心塞进那条 71 mm 带子**。
那一轮烧了 192 s 才走到那 5 秒的窗口。

**附带一条方法论**:同系列的 v49e / v49f 日志都打印了
「穿越脉冲完成: 正前净空 0.94/1.09m, 已穿出」,但它们的 `trace.csv` 显示
**x 最小只有 1.476 / 1.497,从未到过 x<1.30**。算法自报的"已完成"来自它自己的几何判据,
判据错了日志就跟着错 —— **核成绩一定要看轨迹,不要只看日志。**

### D2. 基准图是人工修过的,和真几何有厘米级差异

`env/benchmark_map.pgm` 是在给定 `round1.world` 里实测建图后,按真几何校验做过
**幽灵墙清除 / 墙带减薄 / 空洞填白**;**未改动任何几何**。

维护者 2026-10-04 独立复核(完整表格见 `docs/CONFIG_PROVENANCE.md`):

- **没有假墙**:342 个占据格到最近真墙表面的距离,最大 0.034 m(0.69 格)。
  逐墙法向偏移 p95 在 −13~+12 mm 之间,场地内 unknown 为 0 格。
- **但有缺墙**(第二轮复核才补上,第一轮漏了):沿墙中线采样,**南墙有 1.21 m、
  北道北 1.05 m、岛西 60° 斜墙 0.76 m** 的区段在地图上是 FREE,
  其中 5 处**经 0.20 m 膨胀仍然贯通**。目视复核确认南墙 x∈[−1.50,−1.10] 是
  7×7 全空的完全空洞。

**=> Navfn 在这两处是真的看不见墙。** 这不是算法缺陷,是基准图 + 膨胀参数的性质。
每个新参赛者都会在同一个拐角上重复烧掉几十轮 —— 所以必须先知道这件事。
另外那句"未改动任何几何"也**不准确**:真值墙本身没被动过(法向偏移 ≤13mm),
但修图过程**抹掉或移走了部分墙段**,地图并不等于真几何。

⚠️ **但别把工具报的数字直接当结论**,两个都要小心:

- `check_map_quality.py` 的**"幽灵墙 38%"** 是 0.3 格严判造成的误读 —— 那 130 ��离真墙
  只有 1.5~3.4 cm,是 5 cm 栅格下墙画胖了一点。容差放到 0.8 格就归零。
- **"真墙覆盖率 100%"** 这个说法**没有口径支撑**:维护者用三种口径
  (格重叠 /1 格容差 → 21.4%~95.2%;沿墙长采样 /0.025 m 法向容差 → 42.1%~100%;
  掐掉端头 → 更低)都算不出 100%。覆盖率取决于口径,而原结论没写口径。

**为什么要紧**:凡是"按地图算几何可行性"的结论(能不能过、缝多宽、余量多少),
都可能因这层差异而翻转。**先定地图口径,再谈几何。**

## G. 打榜链路自身的坑(不碰你的算法也会中招)

这一节全是维护者**建仓时**实测出来的, 与算法无关。它们的共同特点是:
**不会让程序崩溃, 只让结果悄悄变成错的。**

### G1. 「跑通了」可能是假的 —— 你读到的也许别人的 ROS 状态

**现象**:容器一律用 `--network host`。同宿主上只要还有**另一场**跑分在跑,
两边的 ROS master 就抢同一个 `11311`。后启动的那一轮, 节点起来后连上的是**对方**的 master,
于是 `rostopic echo /clock`、`/scan`、`/amcl_pose`、`rosparam get /use_sim_time`
全都在读对方的状态。

**实测后果**:建仓时 `harness/headless_nav.launch` 因一次静默失败的 `cp` 根本没进仓库,
`roslaunch` 立刻抛 `RLException: is not a launch file name` 退出。但那一轮日志里依次打出
「gazebo 起来了 use_sim_time=true」「激光就绪」「里程计就绪」「导航栈就绪」「发车! sim_now=68」——
**全部是对方的**。一整轮"验证通过"里没有一秒是自己的仿真。

**为什么没被抓住**:打榜脚本跑在 `set -uo pipefail` 下,**没有 `-e`**。
`roslaunch` 挂了不会中止脚本,它继续往下走 `wait_topic`,而 `wait_topic` 只要话题有数据就返回。

**怎么做**:
1. **串行跑轮。** 这是根本对策。
2. 真要并行:`ROS_MASTER_PORT=11312`(见 `harness/arena_env.sh`),并给容器换 gazebo 端口。
3. 任何"等待某话题出现"的逻辑,都必须先确认**自己拉起的进程还活着**。
   `harness/run_sim.sh` 现在做三重检查: launch 文件存在 → `roslaunch` 进程仍在 →
   `/gazebo` 节点确实在跑。任何一条不满足立刻退出。

### G2. 产物路径写错, 计分会把碰撞算成 0

**现象**:`PRE_RACE` 里的路径是**宿主视角**的,但那段命令在**容器内**执行。
容器里仓库挂在 `/usr/local/share/arena_root`,而 `/home/<用户名>/...` 是容器自己的目录。
于是监视节点把 `trace.csv` 写进了容器的文件系统,宿主上 `runs/<TAG>/trace.csv` 静默缺失。

**为什么没被抓住**:`bench_score.py` 只判断"文件不存在",于是 `collisions = 0`,
看起来就是一个"跑得很干净的成绩"。**一个不会报错、只会让碰撞罚凭空消失的 bug。**

**怎么做**:凡是进容器的路径,一律用容器视角拼(`ARENA_CONTAINER_ROOT`)。
`bench_run.sh` 尾部现在有产物自检,缺文件以非零码退出。

### G3. 地图指针指向仓库外,且 map_server 不报错

**现象**:大会原包的 `ucar_navigation/maps/map.yaml` 里 `image:` 写的是**绝对路径**。
仓库 clone 到别人机器上,那个路径不存在。

**为什么没被抓住**:`map_server` 读不到图**不会报错**,导航栈照样起来,
只是地图全是未知,表现为"车乱撞 / 不动"。而在原机器上一切正常。

**怎么做**:改成相对文件名 `map.pgm`(map.pgm 本身一个字节没动)。
`harness/verify_redline.sh` 现在会核对 `resolution`/`origin`/`negate`/
`occupied_thresh`/`free_thresh` 五项未改,并要求 `image` 是相对路径且文件存在。

### G4. 镜像把 GAZEBO_MODEL_PATH 烤死了

**现象**:赛事参考镜像 `smartcar-noetic-control:v2` 把 `GAZEBO_MODEL_PATH`
烤成它自己那套 `models` 目录。脚本里写 `export GAZEBO_MODEL_PATH="${GAZEBO_MODEL_PATH:-...}"`
**不会**覆盖它 —— 只有变量为空或未设置时才会用默认值。

**后果**:指向一个不存在的目录 → 场地 mesh 与锥桶**全部没有碰撞体** →
激光穿墙、锥桶被撞飞、地图与现实对不上。

**怎么做**:`arena_env.sh` 与 entrypoint 都**强制**赋值(前提是 `$ARENA_ROOT/env/models` 存在),
覆盖入口改用 `ARENA_GAZEBO_MODEL_PATH`。

### G5. `docker exec` 不继承 entrypoint 的环境变量

entrypoint 里 `export ROS_MASTER_URI=...` 只对 entrypoint 自己的进程树有效。
`docker exec` 起的是新进程,拿不到。而打榜脚本在 `set -u` 下引用未定义的
`ROS_MASTER_URI` 会直接 `unbound variable` 退出。

**怎么做**:ROS 相关变量在 `harness/arena_env.sh` 里再兜一次底(且只在容器内设)。

### G6. 首次 clone 慢不是 bug, 是 car3 的网格

仓库 40 MB 里 92% 是 `car3/meshes/` 下 23 个二进制 STL。它是红线组件,
既不能删也不能压(实测最高压缩率重打包只省 13%)。慢速链路上首次 clone 需
35~45 分钟,`git pull` 很快。

**不要**为此改用 Git LFS:LFS 会把这些文件变成指针文件,而本仓库的完整性保证
(`env/REDLINE_SHA.txt` + `verify_redline.sh`)依赖对文件本身的 SHA 校验。
用 LFS 换来的是几分钟,赔上的是"红线组件有没有被改过"这个问题的可核对性。

### G7. `trace.csv` 是**退出时**才落盘的,被硬杀就整条丢失

`harness/bench_monitor.py` 把采样行全部攒在内存里,只在 `rospy.on_shutdown()` 里
一次性写 CSV。所以:

- **跑分进行中** `runs/<TAG>/trace.csv` 是不存在的 —— 这不代表出错。
- 只有正常收尾才会落盘。若进程被 `SIGKILL`(例如被自己的 cleanup 脚本误杀、
  容器被删、或 Ctrl-C 次数不对),**整条轨迹消失**。
- 后果与 G2 一样而且更隐蔽:`bench_score.py` 找不到文件就把 `collisions` 当 0,
  成绩看起来"干净",实际是无效数据。

**这条不能靠改 `bench_monitor.py` 解决** —— 它是红线文件(碰撞口径的载体)。
能做的只有:

1. 让每一轮**正常收尾**,别中途硬杀;
2. `bench_run.sh` 尾部已经加了产物自检:`trace.csv` 缺失时以非零码退出,
   不让这一轮被当成有效成绩。**看到那个报错就当这一轮不存在,重跑。**

### G8. `spawn_cones` 的航点表必须与你的 commander 一致

`harness/spawn_cones.py` 的 `ROUTE` 决定锥桶被摆在哪。改了航点不同步,
锥桶就摆到你根本没走过的位置上,而且**不会报错**。详见 D3。

## E. 复现用的探针(参赛者可以自己做)

维护者自己的探针未随仓库分发(那是算法资产)。下面这些**用仓库现有工具就能做**:

| 想验证什么 |怎么做 |
|---|---|
| 地图与真几何是否一致 | `python3 harness/check_map_quality.py` |
| 某条走廊到底多宽 | `spawn_cones.py --dry-run` 会打印每处摆放的两侧通道宽度 |
| 锥桶摆得合不合法 | `spawn_cones.py --dry-run --seed <S>`(生成器内置校验) |
| 贴墙残差是否正常 | 看你自己 commander 日志里激光互检那一行的 mm 数(正常 1~5 mm) |

## F. 一句话总结

> **不要用几何模型去替成本地规划器。** v2 这一轮有据可查的三次翻车
> (A1 行序、A2 浮点混叠、A3 插值、A4 阈值)全部源自"我以为 costmap_2d 是这么判的"。
> 真要弄明白 planner 为什么不动,就直接订阅 `/move_base/local_costmap/costmap`,
> 在卡死点附近把实际代价值打出来 —— 那比任何离线推导都有说服力。

第二句同样适用于**打榜链路本身**:「跑通了」「指标好看」都要问一句
**它凭什么是真的**。建仓时那次"端到端全绿",靠的是一个不存在文件和别人的 ROS master。
